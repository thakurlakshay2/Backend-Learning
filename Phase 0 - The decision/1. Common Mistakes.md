# Phase 0 - The Decision

## 1. Common Mistakes

### 3 Backend Mistakes That Get Junior Developers Rejected in Code Reviews

If you have ever stared at a code review comment like “this is leaking too much data” or “this should not return 200 for everything,” you already know how brutal backend reviews can feel. The good news is that most of these issues are predictable, and once you learn the patterns, they become much easier to avoid.

This article is written for developers who want to move from “it works” to “it is safe, intentional, and review-friendly.” We will walk through three mistakes that show up constantly in real backend systems and pair each one with a runnable example in this project.

---

## Why These Mistakes Matter

A backend system is not judged only by whether it compiles. In real teams, reviewers care about:

- security
- API clarity
- maintainability
- future scalability
- developer experience for the people consuming the service

The three mistakes below look small at first, but they are exactly the kinds of issues that trigger feedback in code reviews.

---

## 1. Returning Database Entities Directly from the API

This is one of the most common beginner mistakes. A developer fetches a database object and returns it directly from the controller, assuming the client only needs the fields that are currently visible.

### Why this is a problem

The database model is usually more detailed than the public API should be. Returning it directly can expose:

- internal IDs
- password hashes
- audit metadata
- columns that were never meant for external use

It also creates tight coupling between your persistence layer and your API contract.

### The better approach

Use DTOs to shape the response explicitly. A DTO is a simple object that defines exactly what the client should receive.

In this project:

- The bad flow returns the full entity directly from the controller in [../src/main/java/com/example/phase0/controller/UserController.java](../src/main/java/com/example/phase0/controller/UserController.java)
- The safe DTO used for the good response is in [../src/main/java/com/example/phase0/dto/UserResponseDto.java](../src/main/java/com/example/phase0/dto/UserResponseDto.java)
- The service layer that maps the entity into the DTO is in [../src/main/java/com/example/phase0/service/UserService.java](../src/main/java/com/example/phase0/service/UserService.java)
- The domain model being exposed in the bad example is in [../src/main/java/com/example/phase0/model/UserEntity.java](../src/main/java/com/example/phase0/model/UserEntity.java)

### What to learn from this

Think of your API as a contract. The client should receive only the data it needs, and the shape of that contract should be deliberate.

### Try it

Run the app and open:

- http://localhost:8080/users/bad/1
- http://localhost:8080/users/good/1

You will notice that the bad endpoint exposes the full object, while the good endpoint returns a cleaner, safer response.

## 2. Storing Passwords in Plain Text

This mistake is severe because it turns a single vulnerability into a full account compromise scenario. If a password is stored as plain text, anyone who gets access to the database gets access to the actual credentials.

### Why this is a problem

If your database is leaked:

- user passwords are visible immediately
- attackers can reuse them across other services
- the damage is much larger than the original breach

### The correct approach

Passwords should never be stored in plain text. They should be hashed using a one-way algorithm such as BCrypt.

In this project:

- the password hashing logic lives in [../src/main/java/com/example/phase0/service/UserService.java](../src/main/java/com/example/phase0/service/UserService.java)
- the controller exposes a dummy registration and login flow in [../src/main/java/com/example/phase0/controller/UserController.java](../src/main/java/com/example/phase0/controller/UserController.java)

### What to learn from this

A hash is not the same as encryption. A hash is designed to be irreversible, which makes it appropriate for storing passwords safely.

### Try it

Use these endpoints:

- POST http://localhost:8080/users/register?password=hello123
- POST http://localhost:8080/users/login?password=hello123&storedHash=$2a$10$...

The registration endpoint demonstrates the correct flow of hashing before persistence. The login endpoint shows how a login check should compare a user-entered password against the stored hash.

### Recommended reading

- OWASP Password Storage Cheat Sheet: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- BCrypt documentation: https://www.mindrot.org/projects/jBCrypt/

## 3. Returning 200 OK for Everything

This is a smaller-looking mistake, but it creates major confusion in real APIs. Some developers return 200 OK even when the request failed, when input was invalid, or when a resource was created.

### Why this is a problem

HTTP status codes are part of the API contract. They tell clients what actually happened.

If every response looks successful:

- frontend developers cannot reason about failures quickly
- retries may happen incorrectly
- monitoring and debugging become noisy
- your API becomes harder to integrate reliably

### The better approach

Use the correct status codes for the situation.

Examples:

- 201 Created for a successful resource creation
- 400 Bad Request for invalid input
- 401 Unauthorized for missing or invalid authentication
- 404 Not Found for a missing resource
- 500 Internal Server Error for unexpected failures

In this project:

- the bad endpoint returns 200 for every request in [../src/main/java/com/example/phase0/controller/UserController.java](../src/main/java/com/example/phase0/controller/UserController.java)
- the good endpoint returns 400 for invalid input in the same controller

### What to learn from this

Status codes are not cosmetics. They are part of the semantics of your API.

### Try it

Call:

- POST http://localhost:8080/users/bad-status
- POST http://localhost:8080/users/good-status

The first one demonstrates the weak approach, while the second shows how a more professional API communicates errors clearly.

## How These Three Mistakes Connect

These issues often appear together in beginner code:

- the API exposes too much data
- the code stores secrets insecurely
- the response semantics are unclear

That combination is exactly what makes a backend implementation feel immature in review.

A strong backend developer does not only think “does it work?” They also ask:

1. Is this contract safe?
2. Is this data protected?
3. Does this response communicate the truth clearly?

---

## Suggested Learning Path

If you want to build intuition around these ideas, work through them in this order:

1. Understand DTOs and response shaping
2. Learn how password hashing works and why it matters
3. Practice using HTTP status codes intentionally

Once you are comfortable with those three topics, you will already be ahead of many junior developers in code review discussions.

---

## Final Takeaway

The difference between average and strong backend code is often not complexity. It is discipline.

A mature backend developer:

- avoids leaking internal data
- protects credentials properly
- uses HTTP semantics correctly
- writes APIs that are easy for other developers to trust

That is the mindset this project is designed to teach.

Try this as a small self-check:

- Create a `UserResponse` DTO and map a `User` entity into it
- Hash a password using BCrypt before saving it
- Return `201` on successful creation and `400` on bad input

If you can do these three things correctly, you are already thinking like a stronger backend developer.
